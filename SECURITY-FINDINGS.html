What was scanned

Four tools, two targets. grype and syft read the packaged JAR — the artifact that would actually be deployed. trivy and gitleaks read the source tree. That split matters: a scanner pointed at source sees what you wrote, while a scanner pointed at the artifact sees what you shipped, and those are not the same thing.

OWASP dependency-check was not run. It requires an NVD API key; without one, the first run downloads the entire National Vulnerability Database at throttled speed and routinely times out. grype and trivy ship pre-built databases and have no such dependency.

Severity is not urgency

Six findings are labelled Critical. Treating them as equally urgent would be a mistake, and the data says so plainly. CVSS scores how bad exploitation would be; EPSS estimates the probability that exploitation is actually attempted in the next 30 days. They disagree constantly.

Read the rows where the two bars disagree. CVE-2026-65905 scores 9.8 and is almost never exploited. CVE-2021-44832 scores 6.6 and is exploited constantly. Severity and urgency are different questions.

The comparison that matters

CVE-2021-44228 (Log4Shell) and CVE-2026-65905 (Tomcat) are both Critical, 9.8–10.0. But Log4Shell sits at EPSS 100% and carries a KEV tag — CISA has confirmed exploitation in the wild. The Tomcat flaw sits at 0.8% with no KEV tag. That is roughly a 125× difference in the likelihood anyone tries it. A queue sorted by CVSS alone would work on them in the wrong order.

Present is not the same as exploitable

A scanner reports what is on the classpath. It does not know whether your code can reach it. That distinction decides how much of this list is genuinely your problem.

The ten planted CVEs are unreachable. No application class imports commons-collections, commons-text, or log4j-core. The jars sit inside BOOT-INF/lib/ and are never loaded. Log4Shell needs attacker text to reach a Log4j2 logger; this application logs through Logback. There is no path.

The three inherited CVEs are reachable. Every HTTP request to this service passes through tomcat-embed-core. They score lower on likelihood but sit directly in the request path.

So the ranking flips depending on the question. By exploit likelihood, Log4Shell dominates. By reachability in this application, the Tomcat findings are the only ones an attacker could touch. Both readings are correct; a triage process needs both, and neither is what the scanner hands you.

Practical consequence

Unreachable does not mean ignorable. A future feature that adds a dependency pulling log4j-core into the logging path converts a dormant finding into a live one with no visible change to your own code. Unused vulnerable dependencies are removed because they are unused — not because they are harmless.

The allowlist trap

The AWS key was originally set to AKIAIOSFODNN7EXAMPLE — Amazon's own published documentation example, chosen precisely because it matches the AWS pattern exactly. gitleaks reported nothing. It allowlists that exact string by name, because it appears in every AWS tutorial and would otherwise generate endless false positives.

Swapping it for a realistic fake produced an immediate hit: 

gitleaks dir .

aws.access.key  = AKIAIOSFODNN7EXAMPLE   → no finding (allowlisted)
aws.access.key2 = AKIA   → aws-access-token

The lesson is not that the allowlist is wrong — it is correct and necessary. It is that detection depends on shape. Anything with a distinctive prefix gets caught. A password, a JWT secret, or the 40-character half of an AWS pair that actually grants access has no shape to match, and passes straight through.

Secrets survive into the artifact

A JAR is a zip file. Every credential in the source is readable from the shipped artifact with no source access, no decompiler, and no privileged position — only the file. 

$ unzip -p catalog-0.0.1-SNAPSHOT.jar BOOT-INF/classes/application.properties

app.payment.stripe-key=sk_test_

Deleting the field does not delete the secret

PaymentConfig holds its keys in static final String fields. In Java those are compile-time constants, so the compiler inlines them into every class that references them. PaymentService.java never writes the key — but its bytecode contains it: 

$ javap -c -p com.shashi.catalog.payment.PaymentService

public java.lang.String buildAuthorizationHeader();
  Code:
     0: ldc  #9   // String Bearer sk_live_
     2: areturn

There is no field lookup at runtime — the finished string sits in the constant pool. Which means removing the field from PaymentConfig.java leaves the copies already inlined elsewhere untouched until a full rebuild. On an incremental or cache-backed CI build, the "removed" secret ships anyway. That is a documented way credentials outlive the commit that deleted them.

Also worth knowing

On macOS, strings refuses to read .class files: Java's 0xCAFEBABE magic number is also the Mach-O universal binary magic, so BSD strings misparses the header and aborts. GNU strings on Linux reads it fine. A verification step that passes on the CI runner can fail on a developer's Mac for reasons that have nothing to do with the code. Portable alternative: tr -c '[:print:]' '\n' < File.class | grep sk_

The reports are themselves sensitive

Trivy, scanning the working tree, flagged eight secrets in a file that had not existed an hour earlier: 

reports/gitleaks.json   secrets=8   stripe-secret-token

The scanner output quotes the secrets it found, in plaintext, along with their exact file and line. Obvious once stated, and routinely missed in practice — which is how scan reports end up committed to the repository, attached to tickets, or published as public CI artifacts.

reports/ must be in .gitignore before the repository is initialised. A scan report is as sensitive as the secrets it describes.

Remediation

Ordered deliberately. Rotation comes first — it is the only step that actually revokes access. Removing a secret from code while the credential stays valid changes nothing for an attacker who already copied it.

  1. 01 Rotate every exposed credential at its source Revoke the old key at the provider. Skipping this and going straight to code cleanup is the most common real-world failure — the repository looks clean while the credential still works.
  2. 02 Gitignore reports/ before git init The scan output contains the secrets verbatim.
  3. 03 Move properties to environment variables, with no defaults ${DB_PASSWORD}, never ${DB_PASSWORD:changeme}. A fallback lets the application boot on the wrong credential and fail somewhere far from the cause.
  4. 04 Replace the static final constants with injected configuration Constructor-injected @ConfigurationProperties. This is what stops the value being compiled into the bytecode.
  5. 05 Rebuild fully, then re-verify the artifact mvn clean package, then grep the JAR again. An incremental build can retain inlined copies of a constant you deleted.
  6. 06 Upgrade the vulnerable dependencies Remove commons-collections, commons-text and log4j-core entirely — nothing uses them. Bump tomcat-embed-core to 11.0.25 to clear the three inherited Criticals.
  7. 07 Close the actuator exposure management.endpoints.web.exposure.include=health,info and remove show-values=ALWAYS. Exposed, it returns every credential over unauthenticated HTTP.
  8. 08 Purge the secrets from git history Deleting a file does not remove it from earlier commits. git filter-repo, then confirm with gitleaks detect, which scans history rather than the working tree.
  9. 09 Add a gitleaks pre-commit hook Prevention, so this cannot recur silently.
  10. 10 Re-run every scanner and diff against this baseline The proof is the difference between two reports, not the absence of findings in one.

Dependencies

commons-collections, commons-text and log4j-core were removed outright — direct dependencies referenced by no application code. tomcat-embed-core could not be removed; it arrives transitively through spring-boot-starter-webmvc. It was bumped 11.0.24 → 11.0.25 by overriding the tomcat.version property that Spring Boot's BOM manages. That is the supported mechanism — an explicit <dependency> block also works, but you then own that version permanently, including across Boot upgrades that would otherwise move it for you.

The compiled constant

PaymentConfig's static final String fields became PaymentProperties, a @Validated @ConfigurationProperties record injected by constructor. The bytecode is the proof: 

before  0: ldc           #9   // String Bearer sk_live_<redacted>

after   1: getfield      #7   // Field properties:...PaymentProperties
        4: invokevirtual #13  // Method ...stripeKey()

A compile-time constant is baked into the constant pool of every referencing class. A field read resolves at runtime, so there is no literal left to find.

The four passwords no scanner found

docker-compose.yml now reads docker/postgres/.env through env_file, and the initdb script was converted from .sql to .sh — Postgres executes .sql files literally and cannot expand a variable, which is why the passwords had to be written into it in the first place.

These four are worth singling out: both scanners missed all of them at baseline. SQL CREATE USER … PASSWORD and plain YAML assignments match no rule in either default ruleset. They were fixed only because the planted secrets were enumerated by hand and checked off one by one. Nothing in the tooling would have raised them.

What is still reported, and why that is correct

gitleaks dir . still returns 30 findings. All 30 are in .env, docker/postgres/.env and reports/ — gitignored, never committed, confirmed against git ls-files. Two behaviours worth knowing: trivy does not respect .gitignore, so it scans local-only files; and trivy caught aws-secret-access-key in .env having missed the same secret in application.properties at baseline. The variable name AWS_SECRET_KEY= gave its rule the context that app.aws.secret-key= did not.

What this exercise did not prove

The scanners never found 10 of the 13 planted credentials. Remediation was driven by an inventory kept by hand, not by the reports. In a real codebase with no such inventory those ten would still be there — and every scan would have come back clean.

A clean scan is evidence that the scanner found nothing. It is not evidence that there is nothing to find.
